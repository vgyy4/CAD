# ADR 0011: Hardware baselines, CPU dispatch, quality tiers and thread priorities

- Status: proposed (draft)
- Date: 2026-10-10
- Research: `docs/research/mcp-simd-storage-crates.md` §2; `docs/HARDWARE.md`
- Code: `crates/gusset-hw`

## Context
The spec makes integrated-GPU laptops (4 cores, 8 GB shared RAM, Intel HD 520-class
iGPU) the reference machine and asks that better hardware automatically get a faster,
nicer experience without making old hardware worse. It also requires that code which
defines the model gives the same result on every CPU, and that the hardware
documentation is generated from (or tested against) a single registry in the code.

## Decision

### 1. Build baselines
- **x86-64: `x86-64-v2`** (SSE4.2, POPCNT, SSSE3, CMPXCHG16B, LAHF/SAHF), set per
  x86_64 target triple in `.cargo/config.toml` with `-C target-cpu=x86-64-v2`. Listing
  triples explicitly (`[target.x86_64-unknown-linux-gnu]`, `-pc-windows-msvc`, ...)
  leaves every other target, including all aarch64 targets, untouched.
  v2 covers every Intel Core and AMD Bulldozer-or-later CPU we target; v3 (AVX2) would
  drop Sandy/Ivy Bridge and AMD FX machines that are still in use, which the spec
  forbids.
- **aarch64: ARMv8.0-A + NEON**, the Rust default for `aarch64-*` targets. Nothing is
  configured. This runs on Raspberry Pi 4 (Cortex-A72) and up.
- `RUSTFLAGS` replaces config rustflags. CI jobs that set `RUSTFLAGS` must repeat
  `-C target-cpu=x86-64-v2`.
- C/C++ dependencies (OCCT) are built for the same baseline and get no per-CPU flags.

### 2. Runtime dispatch
- **Levels:** `scalar`, `sse42` (x86 baseline), `avx2fma`, `avx512` (F+BW+VL), `neon`
  (aarch64 baseline), `neon-dotprod`, `sve`. The required features of each level, the
  code paths that use it, its determinism status and its measured speedup live in one
  static table, `gusset_hw::registry::DISPATCH_PATHS`. Detection
  (`gusset_hw::cpu`), selection (`gusset_hw::dispatch`) and the doc generator all read
  it.
- **Detection:** `std::arch::is_x86_feature_detected!` /
  `is_aarch64_feature_detected!` for SSE4.2, POPCNT, AVX, AVX2, FMA, AVX-512F/BW/VL,
  AVX-VNNI, NEON, DotProd, I8MM, SVE, SVE2. The level is chosen once at startup
  (`dispatch::init` / `dispatch::active`, a `OnceLock`).
- **Mechanism (this ADR): safe `#[target_feature]` functions** (target_feature 1.1,
  stable since Rust 1.86). Each kernel body is written once as an `#[inline(always)]`
  generic function and instantiated inside per-level `#[target_feature(enable = ...)]`
  wrappers; LLVM autovectorizes it for that level. The only `unsafe` is the call from
  non-target-feature code, and that call site re-checks the exact features with
  `is_*_feature_detected!` immediately before calling, so soundness never depends on a
  correct `Dispatch` value being passed in. One macro (`variant!` in `kernels.rs`)
  generates these call sites so their `// SAFETY:` argument is written once.
  - We do not add `multiversion` or `fearless_simd` yet. The research recommends
    `fearless_simd` for hand-written SIMD kernels and `multiversion` for plain loops.
    The first real hot kernels (tessellation, BVH) should be benchmarked with plain
    target_feature autovectorization first; if explicit SIMD is needed, `fearless_simd`
    (Apache-2.0 OR MIT, MSRV 1.89) is the preferred addition, verified at that time.
  - SVE code is generated by autovectorization under `#[target_feature(enable = "sve")]`;
    SVE intrinsics are nightly-only (research §2).
- **Keep only what helps:** every non-scalar level starts as "not yet measured" in the
  registry. A criterion benchmark per dispatched path fills in the speedup (benchmark
  name and machine). A level that does not measurably help is removed from that code
  path.
- **AVX-512 is a bonus**, never expected (absent on consumer Intel 12th–14th gen and
  Core Ultra; see `docs/HARDWARE.md`).
- **MSRV:** `gusset-hw` declares `rust-version = "1.89"` (AVX-512 target features and
  `avxvnni` detection stabilized in 1.89; checked with `cargo +1.89 check`). The rest of
  the workspace stays at 1.85 until a workspace-wide MSRV ADR. `__cpuid` is wrapped in
  `unsafe` because it is still an `unsafe fn` in 1.89 (safe in newer std).

### 3. Determinism policy
- **Model-defining code never uses a dispatched or FMA path.** This covers kernel
  operations, constraint solving, feature evaluation, anything affecting topology,
  persistent naming, or saved files. It calls scalar code directly (or its own
  non-dispatched code) and never consults `dispatch::active()`. Rust never contracts
  `a * b + c` into an FMA on its own, so scalar code is reproducible across CPUs given
  the same baseline; explicit `mul_add` is forbidden in model-defining code.
- **Display-only code may use any level:** viewport meshes, rendering, picking. Each
  display kernel documents its tolerance against scalar (the demo kernels: per
  coordinate, `8 * f32::EPSILON * (|m0*x| + |m1*y| + |m2*z| + |t|)`; pure comparisons
  such as bounding boxes are bit-identical).
- The registry records the determinism status per level; a unit test enforces that only
  `scalar` is marked model-defining.

### 4. Forcing a path (tests and CI)
- `dispatch::choose(features, forced)` takes the value of the app's
  `--force-dispatch <level>` CLI flag (any build). An unknown or unsupported level is an
  error, never a silent fallback, so CI cannot accidentally test the wrong path.
- `GUSSET_FORCE_DISPATCH` is read by `dispatch::env_override()` **only when
  `debug_assertions` is on** (debug/test profiles). Release builds never consult it, in
  line with the spec's rule that release builds do not take behavior from environment
  variables.
- **CI determinism job:** for each level in `dispatch::supported_levels()` of the
  runner (x64 runners cover `scalar`/`sse42`/`avx2fma`, and `avx512` where the runner
  CPU has it; ARM runners cover `scalar`/`neon`/`neon-dotprod`), run the golden geometry
  suite with `GUSSET_FORCE_DISPATCH=<level>` and compare the results with the scalar
  run: model-defining outputs must be bit-identical, display outputs within each
  kernel's tolerance. The kernel unit tests already iterate every supported level in-process.

### 5. GPU quality tiers
- Tiers `low`, `medium`, `high` live in `gusset_hw::registry::GPU_TIERS` with their
  effects (MSAA, SSAO, shadows, LOD factors, render scale while moving) and the adapter
  classes that get each tier automatically: software/integrated/virtual/unknown → `low`,
  discrete → `high`, `medium` manual only for now. The user can override the tier.
- Only wgpu downlevel limits are requested; optional features are used behind runtime
  capability checks (e.g. 8x MSAA falls back to 4x).
- The renderer fills `GpuDiagnostics` (adapter, backend, class, driver, tier, failed
  backends) into the diagnostics report.

### 6. Resource budgets
Pure functions in `gusset_hw::budgets`: interactive pool `max(1, logical - 1)` (one CPU
stays free for the UI); background pool = E-core count on hybrid CPUs, else half the
interactive pool, clamped to `[1, interactive]`; cache = RAM/16 clamped to
[128 MiB, 4 GiB] (GPU memory is system RAM on the reference machine); default
tessellation quality and speculative precompute scale with cores and RAM. Unknown RAM is
treated as 4 GiB.

### 7. Thread priorities
Background work (pre-tessellation, thumbnails, autosave, indexing) runs on threads that
lower their own priority (`priority::spawn_background` /
`lower_current_thread_priority`), so the OS can place them on E-cores:
- Linux: `setpriority(PRIO_PROCESS, gettid(), 10 | 19)` (per-thread on Linux).
- macOS: `pthread_set_qos_class_self_np(QOS_CLASS_UTILITY | QOS_CLASS_BACKGROUND)`.
- Windows: EcoQoS via `SetThreadInformation(ThreadPowerThrottling,
  EXECUTION_SPEED)` plus `SetThreadPriority(BELOW_NORMAL | LOWEST)`.
- Other platforms: no-op (`PriorityOutcome::Unsupported`).
Priority is only ever lowered, never raised.

### 8. Unsafe code and dependencies
The workspace forbids `unsafe_code`; `gusset-hw` sets it to `deny` (crate-level
`#![deny(unsafe_code)]`) and allows it only in `src/sys/{linux,apple,windows,x86}.rs` and
the macro-generated kernel call sites. Every block has a `// SAFETY:` comment
(`clippy::undocumented_unsafe_blocks = "deny"`).

New dependencies, both verified on crates.io (2026-10-10) and dual MIT OR Apache-2.0:
- `libc` 0.2.190 (owner `rust-lang-owner`, repository rust-lang/libc), Linux and
  Apple only: `setpriority`, `gettid`, `sysctlbyname`, `pthread_set_qos_class_self_np`.
  Already in the lockfile transitively.
- `windows-sys` 0.61.2 (owner `kennykerr`, repository microsoft/windows-rs), Windows
  only, features `Win32_Foundation`, `Win32_System_Threading`,
  `Win32_System_SystemInformation`.

## Consequences
- Old CPUs keep working at the scalar/SSE4.2 or NEON level; newer CPUs get faster
  display paths without changing model results.
- Every new dispatched path needs a registry row, a benchmark and a regenerated
  `docs/HARDWARE.md` (CI fails otherwise).
- Windows physical-core and P/E topology detection is not implemented (reported as
  unknown); background pools fall back to the non-hybrid rule there.

## Open questions
- Whether `fearless_simd` should replace hand-rolled target_feature wrappers once real
  hot kernels exist (decide with benchmarks).
- Auto-selection of `medium` for strong iGPUs (Apple, Intel Arc/Xe, AMD RDNA iGPUs)
  after measuring them.
- Windows `GetLogicalProcessorInformationEx` parsing for P/E topology.
