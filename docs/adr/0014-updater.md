# ADR 0014: In-app updater

- Status: accepted
- Date: 2026-10-10

## Options evaluated
| Option | Notes | Verdict |
|---|---|---|
| `tough` (TUF client, MIT/Apache) | Full TUF roles, threshold signing, rollback/freeze protection. Heavier; needs a TUF repository layout and role management | concepts adopted; full TUF later if we add mirrors or multiple signers |
| `velopack` (MIT) | Installers + delta updates for all OSes; packaging CLI `vpk` is a separate tool whose distribution must be vetted; its own signing model | not now; revisit for delta updates |
| `self_update` (MIT) | GitHub-releases self-replace, zipsign signatures | too narrow (no per-install-type logic, no self-test/rollback) |
| `cargo-packager-updater` | quiet since 2025 | no |
| **Own updater (`gusset-update`) on `minisign-verify` (MIT, zero-dep)** | Small, auditable, covers our exact rules | **chosen** |

## Decision
1. **Manifest** (`update-manifest.json`, published to GitHub Releases), signed with
   Ed25519 (minisign format):
   `{ channel, version, released, expires, min_supported, revoked_keys[], targets: { "<os>-<arch>-<install_type>": { url, size, sha256, sig, files: [{path, sha256, size}] , delta_from?: {...} } } }`.
   - The app holds **several public keys** (current and next) compiled in. A signed
     revocation list inside the manifest can retire keys, but cannot add new ones.
   - Checks: signature valid against a non-revoked built-in key; `expires` in the future
     (freeze protection); version strictly newer than installed (rollback protection);
     the target matches OS, architecture and install type.
2. **Checking:** the first check runs 2 minutes after startup, then every 6 h by default,
   only while the app runs (no daemon, service or task). Channels are Stable and
   Nightly. Settings explain that the check contacts GitHub, and automatic checks can
   be turned off; "Check now" is always available. Requests carry no IDs and no
   telemetry. HTTP uses `ureq` + rustls + `rustls-platform-verifier`.
3. **Prompting:** a non-blocking notification with the version, notes and the choices
   Install now / Later / Skip this version. It never appears during an operation, a
   command dialog or a sketch; it waits for an idle moment.
4. **Downloading:** background, low priority, resumable (HTTP Range), pausable,
   bandwidth-limited, deferred on metered connections where the OS reports it. Files go
   to `<data_dir>/updates/` (owner-only) under random names. The package is opened
   exclusively, and verified (size, SHA-256, Ed25519) **from the same open handle**
   right before installation. On failure: discard, retry once, then report.
5. **Applying, per install type:**
   - Windows per-user MSI/zip and Linux AppImage: self-replace of the install directory.
     The new version is extracted (safe extraction: no `..`, no absolute paths, no
     links or devices; caps on size and file count; per-file hashes checked against the
     signed list) into a sibling `versions/<v>` directory, and a small launcher switches
     the active version.
   - macOS: the `.app` bundle is replaced atomically (rename the new bundle in, keep the
     old one until the self-test passes).
   - Machine-wide Windows MSI: elevation is requested only at apply time, with an
     explanation.
   - `.deb`/`.rpm`/Flatpak: notify only, with instructions; package-managed files are
     never touched.
6. **Self-test before committing:** re-hash all installed files, then run
   `gusset --self-test`: load the kernel, render one offscreen frame with the software
   renderer, open and rebuild the bundled sample, and start the MCP server on a test
   port. Only then switch and delete the old version; otherwise roll back
   automatically and report.
7. **Restart now** goes through the unsaved-changes close flow (cancel keeps the update
   staged) and reopens the projects afterwards. "Next start" applies before the main
   window opens.
8. **Logging:** every verification step is written to a local, size-capped update log,
   visible in Diagnostics and never sent anywhere.
9. **Delta updates:** planned with zstd `--patch-from` per changed file, listed in the
   manifest and verified exactly like full packages. The full package is always the
   fallback.

## Key management
- The keypair is generated by the maintainer (we will ask the owner once to add the
  secret key to the protected `release` environment as `UPDATE_SIGNING_KEY`). The
  public key is committed in `crates/gusset-update/keys/`.
- **Rotation:** ship release N with keys {old, new} → sign with new from N+1 → after
  the support window, ship a release that drops old.
- **Compromise:** publish a manifest signed by a non-compromised key that revokes the
  compromised one, then rotate. Because revocation can only remove keys, a stolen key
  cannot add new keys.
- Until the secret exists, release workflows build unsigned manifests and the app
  refuses them. No update is ever installed unverified.
