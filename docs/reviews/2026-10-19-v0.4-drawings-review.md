## HIGH

### D1. Scales have no upper bound: dashes, deflection and hatch counts grow with the scale, and the rasterizer can loop forever
- The bounds checks:
  - `crates/gusset-drawing/src/lib.rs:262-268` (`view_scale`) and `lib.rs:569-582` (sheet scale)
    accept any positive finite number.
  - `drawing.create`, `drawing.edit` and `drawing.edit_view` (`commands/drawing.rs:127, 220-224,
    415-419`) parse any expression.
  - `validate_drawings` checks no scale.
  - `scale: 1e300` parses, validates and builds.
- Four costs grow with the scale:
  1. **CPU raster (MCP `render_view`).** `raster.rs:93-127` (`Layer::path`) cuts every dashed
     primitive (hidden lines, centre marks and centrelines, the cutting-plane line, dangling
     dimensions) into dashes along its whole length, with no clipping to the image.
     - A line of length L pixels makes L / period quads.
     - When the length overflows to infinity (scale 1e300 on a 10 mm edge: `dx` is 1e301,
       `dx*dx` is inf), `while t < l` never ends. `t += step` stops changing `t` near 1e16, so the
       loop spins and pushes quads until the process runs out of memory.
     - Reproduced: `raster::render` of one `Style::Hidden` line from (0, 0) to (1e300, 1e300) did
       not return within 10 s. Memory grew until the test process was killed (SIGKILL).
     - Reproduced: a 1e7 mm hidden line (a 100 mm hidden edge at scale 1e5) takes 7.8 s at width
       512 (debug build). The time grows linearly, and so does memory (32 bytes per quad edge).
  2. **MCP plumbing.** `crates/gusset-mcp/src/server.rs:976-983` runs the raster in
     `spawn_blocking` with no timeout. `render_view` holds its render slot (`server.rs:889`) until
     the raster returns, so each such call takes one slot and one blocking thread for good. An
     agent needs two calls: `drawing.edit_view {scale: "1e300"}`, then `render_view {drawing}`.
     That takes down the host process, and with it the user's app session when it is in-process.
  3. **App.** `crates/gusset-app/src/sheet.rs:240-246` uses `Shape::dashed_line`, which also walks
     the whole on-screen length. A hostile `.gus` whose drawing has `scale: 1e300` hangs the UI
     thread when the Drawing tab opens it. At ordinary hostile scales (1e6) it builds millions of
     shapes per frame.
  4. **Kernel and hatching.**
     - `lib.rs:402` passes `deflection: 0.02 / scale` to the kernel. The shim only checks
       `deflection > 0` (`gusset_occt.cpp:2001`), and `GCPnts_QuasiUniformDeflection`
       (`gusset_occt.cpp:1904`) samples every non-line, non-circle edge (ellipses in iso views,
       B-splines) with that deflection. At 1e-12 mm that is millions of points per edge, built in
       the worker and sent back over the wire.
     - `section::hatch` (`section.rs:126-129`) caps lines per triangle at 100 000 but not in total.
       A large scale on a section with many cut-face triangles gives millions of `Prim::Line`s,
       then the same again in SVG, DXF and PDF text.
     - A triangle that needs more than 100 000 lines is skipped silently, so large faces lose
       their hatching.
- Fix:
  - Bound every scale in `validate` and in `view_scale` and the sheet scale (for example
    1e-4..=1e4; ISO 5455 scales are 1:10000 to 50:1). Report the bad value as an issue, the way a
    zero scale is reported.
  - In `raster.rs`, clip each primitive to the image (plus the stroke width) before cutting
    dashes. Cap dashes per primitive (draw it solid beyond, for example, 10 000 dashes) and refuse
    non-finite coordinates. Do the same for the app (`sheet.rs`): clip to the visible rect before
    `dashed_line`.
  - Give `render_drawing` a time limit around the raster as well, or a cancel flag polled per
    primitive.
  - Clamp the HLR deflection from below, relative to the model's size (for example
    `max(0.02/scale, 1e-6 * bbox diagonal)`), and in the shim too.
  - Cap the total number of hatch segments per view, and report a skipped triangle as an issue.

### D2. The cycle check in `validate` is cubic in the number of views
- `crates/gusset-doc/src/validate.rs:420-447`: for every projected or detail view, the code walks
  the chain of parents up to `d.items.len()` steps. Each step calls `Drawing::view`
  (`drawing.rs:65-70`), a linear scan of the items. A chain of n projected views (each `of` the
  previous one) costs about n³/6 string comparisons.
- `validate` runs on every `Document::from_text` (`gusset-doc/src/lib.rs:58`, including the code
  view and documents from MCP) and on every commit (`session.rs:343`). It runs on the model thread
  and cannot be cancelled.
- Reproduced (release build): a drawing of 3000 chained views takes 8.0 s to validate. The sheet
  build itself takes 15 ms. At the 10 000-item limit (`MAX_DRAWING_ITEMS`) this is about 5 minutes,
  and every drawing in the document pays it separately. The text is about 50 bytes per view, so a
  500 KB file costs 5 minutes for every edit an agent or the user makes. Each drawing adds another
  5 minutes, so ten such drawings in 5 MB cost about 50 minutes per edit.
- The scene builder's recursion over the same chain is fine. 9999 chained views build in 0.2 s on a
  2 MiB stack in debug and in release.
- Fix: build a `BTreeMap<&str, &ViewDef>` once per drawing, and colour the parent graph
  (visited/done), so the check is O(n log n). Better still, cap the chain depth (for example 32): a
  projected view of a projected view of ... has no drafting use beyond a few levels.

## MEDIUM

### D3. Building a sheet has no work limit and cannot be stopped
- `gusset_drawing::build` (`lib.rs:566-701`):
  - It projects every view with an exact HLR: 0.1-0.7 s per view for a part of a few hundred faces
    (ADR 0032), far more for assemblies.
  - It cuts every section view with a boolean and a tessellation.
  - It never polls a cancel flag, and the work is not charged to the evaluation budget
    (ADR 0020).
- The cache (`lib.rs:33, 73-101`) keeps the 64 most recent (shapes, axes, deflection) keys.
  - The deflection depends on the view's scale, so views of one direction at different scales do
    not share an entry.
  - A drawing with more than 64 distinct keys evicts its own entries during the build, so every
    rebuild re-projects every view.
  - A hostile document can hold 10 000 views with scales 1.0001, 1.0002, and so on: 10 000 exact
    HLRs, hours with OCCT, on every `query.drawing`, `render_view`, export and Drawing-tab refresh.
- MCP: `render_drawing` (`server.rs:960-972`) wraps the build in `request_deadline`. On timeout the
  agent gets an error, but `exec_async_stoppable` only sets the rebuild cancel flag, which `build`
  never reads. The model thread stays busy and every later command queues behind it.
  `query.drawing` is a READ command and does the same work with no deadline at all.
- The app builds the sheet on the model thread whenever the model changes while the Drawing tab is
  open (`app.rs`, `request_sheet`).
- Fix:
  - Pass the session's cancel flag into `build` and check it between views (and between hatch
    triangles).
  - Charge each HLR and section to a per-build budget, and cap views per drawing (for example
    200). The 10 000-item cap is for dimensions and notes.
  - Key the cache on the deflection rounded to a few steps (or project at the finest scale of each
    direction and reuse it), and size it to the drawing.

### D4. Renaming or deleting a feature that a drawing refers to is refused
- `crates/gusset-commands/src/commands.rs:2197-2229` (`rename_in_doc`) updates the features and
  nothing in `doc.drawings`. Dimension references (`edge(Plate/cap(end), Plate/side(S/l5))`) and
  base-view `bodies` keep the old name.
- `validate_drawings` then reports "dimension D1 refers to 'Extrude1', which does not exist", and
  the commit is refused.
- Reproduced: plate, a drawing view and a length dimension on
  `edge(Extrude1/cap(end), Extrude1/side(Sketch1/l5))`.
  - `feature.rename Extrude1 → Base` fails with `invalid_document`.
  - So does renaming the sketch `Sketch1 → Prof`.
  - The command's description promises "all references (profiles, edges, faces, bodies) are
    updated".
- `feature.delete` of a feature only a dimension refers to gives the same generic
  `invalid_document` error. The "used by" list does not name the drawing. ADR 0032 says the
  dimension should dangle instead.
- Fix:
  - Rename inside drawings too: `EdgeRef::rename_feature` on `a`/`b`, and the base views' `bodies`
    (when they name the feature).
  - For deletion, either list the drawing items in the "used by" error, or let `validate` accept
    references to missing features in dimensions (they dangle, as the ADR says), keeping the check
    only for view `bodies`.

### D5. Dangling dimensions disappear from the sheet unless their text was moved
- `crates/gusset-drawing/src/dims.rs:192-206`: when `build` fails (an edge no longer resolves), the
  dangling marker ("D1?") is drawn only `if let Some(t) = text_at`.
  `drawing.add_dimension` always creates dimensions with `text_at: None`
  (`commands/drawing.rs:537`). So a dimension that was never dragged leaves no trace on the sheet,
  in SVG/DXF/PDF exports, or in the PNG agents see.
- ADR 0032 §1: "It is drawn in the dangling style with '?'". The research note says the most
  common complaint about drawings is dimensions that silently go wrong after a model change. The
  only remaining signals are `issues` (the app shows the first three) and `query.drawing`.
- Fix: keep the last good position. Store nothing in the document, but place the marker at the
  view's centre or at the dimension's default offset beside the view box. Draw the label with the
  stored prefix and the last measured text if the app has it. Add a test that the dangling text
  is in the scene with `text_at: None`.

### D6. The DXF reader's memory is about 23 times the file size
- `crates/gusset-drawing/src/dxf_read.rs:130-164`:
  - The whole file becomes a `Vec<(i32, &str)>` of every pair (24 bytes per pair).
  - The ENTITIES section is then copied again into `Vec<(&str, Vec<(i32, &str)>)>`, with one entity
    (16 + 24 bytes) per group 0.
  - `from_utf8_lossy` copies the file once more when it is not valid UTF-8.
  - Only curves and polyline vertices are capped. Skipped entities and their groups are not.
- Reproduced (release build): 64 MiB (the `MAX_DXF_BYTES` cap, `commands.rs:1476`) of `0\n\n`
  pairs after `SECTION/ENTITIES`. `read` takes 4.4 s and peak RSS grows from 3.5 MB to 1.47 GB.
- The reader runs in-process (ADR 0032 phase 4 chose that over the import worker). A DXF from
  anywhere is imported by the user, or by an agent from the project folder.
- Fix: stream the pairs. Iterate the lines once, keep only the current entity's groups, and skip
  groups of entities that are not read. Cap the number of entities (read or skipped) and of groups
  per entity, and check the cancel flag (`read_capped` is given a fresh, never-set flag at
  `commands.rs:1494`).

## LOW

### D7. A section letter the text form cannot read back
- `commands/drawing.rs:335` accepts 1-8 ASCII letters or digits. The printer writes
  `section: {label}` bare (`gusset-doc/src/drawing.rs:442`), and the parser reads it with `ident()`,
  which needs a letter or `_` first.
- Reproduced: `drawing.add_view {of: F, side: top, section: "1"}` fails with code `history`:
  "a drawing would not read back: line 3, column 42: expected a name, found '1'". The staging check
  works (nothing is committed), but the agent gets an internal-looking error for valid-looking
  input.
- Fix: require a leading letter in the command (and in `validate`), or print the label quoted.

### D8. Views derived from a detail view
- `validate` and `drawing.add_view` let `of:` name a detail view, and `section:` sit on a view
  projected from a detail. `place_one` (`lib.rs:351-391`) then projects the whole model at the
  detail's scale (twice its parent's), aligned with the detail circle's box. That is not a drawing
  anyone wants.
- A detail of a section view copies only the curves (`lib.rs:292-327`), so the enlarged cut has no
  hatching.
- Fix: refuse `of:` a detail view in `validate`. For a detail of a section, clip the section's
  hatch segments to the circle too.

### D9. Section cut faces and planes on the wrong side
- `section.rs:95`: `tol = 1e-3 * (1 + |c|)`. At `cut_at: 500 mm` any part face parallel to the plane
  within 0.5 mm counts as cut and is hatched.
- `section::cut` (`section.rs:60-90`) refuses `c <= lo`. For `c >= hi` (the plane beyond the side
  facing the viewer) nothing is removed and no face lies in the plane, so the view is labelled "A–A"
  with no hatching and no issue.
- Fix: use an absolute tolerance tied to the tessellation (for example 1e-4 mm plus the f32
  rounding of the coordinates). Report `c >= hi` as "the cutting plane misses the part".

### D10. DXF entities in a mirrored OCS, and nearly straight bulges
- `dxf_read.rs:171-231` ignores the extrusion direction (groups 210/220/230). Arcs, circles and
  LWPOLYLINEs with extrusion (0, 0, -1) are common in files from mirrored geometry. They come in
  mirrored about Y (their X is negated in WCS), and arcs run the wrong way.
- `bulge_curve` (`dxf_read.rs:89-106`) turns any |bulge| ≥ 1e-12 into an arc. A bulge of 1e-11 on a
  1 mm chord gives a radius of 2.5e10 mm. Its centre then fails `add_point`'s ±1e9 bound
  (`commands.rs:530`), and the whole import fails with "coordinates must be finite and within
  ±1e9 mm".
- Fix: apply the arbitrary-axis rule for 230 < 0 (negate X of points and swap/negate the angles).
  Treat arcs whose sagitta is below the import tolerance (for example 1e-6 mm) as lines.

### D11. A tiny arc becomes a full circle
- `commands.rs:1534-1543`: an ARC whose two ends round to the same 1 µm key (`a == b`) is added as a
  full circle. An arc of 0.0001° on a 10 mm radius (ends 17 nm apart) becomes a 20 mm circle.
- Fix: decide from the angles, not the rounded ends: a sweep of at least 360° minus a tolerance is a
  circle. A sweep near 0 is dropped (or kept as a point).

### D12. Dangling text in SVG is hollow and dashed
- `svg.rs:48-70`: every style except `Style::Text` gets a stroke group with `fill="none"` and the
  style's dash array. `dims.rs:194` pushes the dangling marker as `Prim::Text` with
  `Style::Dangling`, so it is written in that group: an unfilled, dashed outline in magenta. PDF
  sets both fill and stroke colours and draws it fine. DXF writes TEXT on layer DANGLING (fine).
- Fix: in SVG, write text primitives with an explicit `fill` (the style's colour) and
  `stroke="none"`, whatever group they are in.

### D13. Older builds call a snapshot with drawings corrupt
- `gusset-history/src/objects.rs:330-343` appends `drawings <hash>` to the `snapshot 2` text. A v0.3
  reader (`objects.rs:379` before this change) refuses any extra line as "corrupt: trailing
  lines". So a v0.4 project with a drawing, opened in v0.3, reports a damaged history, not "made by
  a newer version". The project's damage fallbacks (recovery copy, older node) may then kick in on
  a healthy file.
- Fix: bump the snapshot to version 3 when it has drawings (v0.3 then reports an unknown
  version), or bump the container's format version so older builds refuse cleanly.

### D14. The HLR cache keeps old models alive; worker replies are trusted
- `HlrCache` (`lib.rs:53-126`) holds `Vec<Shape>` for up to 64 projections and 64 cuts. Each edit
  makes new shapes, so the cache pins up to 128 old revisions of the model's bodies (in the kernel
  worker's memory for a remote kernel). `Session::invalidate_cache` (`session.rs:393`) does not
  clear it, and nothing does on undo, branch switch or project close.
- `HlrCurve::get` (`gusset-kernel/src/wire.rs`, after `impl Wire for HlrView`) accepts any f64.
  `ccw_angles` (`lib.rs:204-210`) and `detail::clip` (`detail.rs:189-192`) run `while e <= s
  { e += TAU }`, which never ends for `s = inf`. It runs about 1e15 times for `s = 1e16`, and from
  then on adding `TAU` no longer changes `e`, so it loops forever. The OCCT shim only produces
  `atan2` values, so this needs a faulty worker, but the worker exists to contain faults.
- Fix: drop cache entries whose shapes are no longer in the current evaluation (or clear the cache
  on every commit/branch switch), and clear it in `invalidate_cache`. Reject non-finite curve
  values when decoding, and normalise angles with `rem_euclid(TAU)` instead of loops.

## NIT

- **N1** `dxf.rs:43-56`: `%%c`, `%%d`, `%%u` in user text are DXF control codes in TEXT, so
  "100%%" or "%%u" change what AutoCAD shows (write `%` as `%%%`). Characters outside the BMP are
  written as two `\U+D8xx\U+DCxx` surrogates, which readers do not join. Write `?` or the
  BMP-only form.
- **N2** `gusset-doc/src/drawing.rs:608-622`: a detail view rejects `from/side/gap/bodies/section`
  but silently drops `of:` and `cut_at:`. Both are lost on the next print.
- **N3** `dims.rs:365-403`: an angle dimension's automatic text sits `radius + 2 + TEXT_H/2` from the
  vertex, and that point is reported as `text_at`. Given back as `text_at`, it becomes the arc
  radius, so the first drag moves the arc 3.75 mm outwards.
- **N4** `lib.rs:164-172` (`number`): `cut_at`, detail `center` and `radius` are "model mm" (grammar
  says so), so `radius: 0.5` in an inch document is 0.5 mm. Same class as review v0.3 M4: take plain
  numbers in the document unit for model quantities.
- **N5** ADR 0032 §2 keeps `HLRBRep_PolyAlgo` "for very large views only", but `lib.rs:402` always
  sends `exact: true`. Either select it from the face count or drop the claim from the ADR.
- **N6** Tests:
  - `a_dxf_file_becomes_sketch_geometry` (`tests_drawing.rs:156`) never removes its temp folder.
  - `a_dimensioned_sheet_of_a_plate_with_a_hole` asserts `second < first` on wall time.
  - `dxf_read::tests::our_own_exports_read_back` reads a hand-written string, not an export (the
    commands test does read an export, but only checks `lines > 20`).
  - Sections and the cutting-plane arrows are tested only with OCCT (the mock cannot cut). The
    arrow direction and the third-angle placement of a section are not asserted anywhere.

## Checked and found sound
- **Text form.** Strings go through `quote`/`Cursor::string` (escapes for `"`, `\`, `\n`, `\t` and
  other control characters). Note text may hold `\n`; titles, numbers, tolerances and prefixes may
  not (`validate.rs`). Every staged drawing object is parsed back before it is committed
  (`objects.rs`, `ObjectKind::Feature if text.starts_with("drawing ")`). So the item cap, odd
  labels and other print/parse asymmetries fail the command instead of committing an unreadable
  node (the class of review v0.3 H2).
- **History.** The snapshot closure includes the drawing list (GC keeps drawings). Diff, compare
  and three-way merge treat drawings as whole objects, like configurations, and record taken
  drawings in `from_theirs`. Merged documents still go through `validate` at commit.
- **Paths.** `drawing.export` uses `export_target` with `svg/dxf/pdf` only. For agents it is
  confined (no `..`, absolute paths, symlinked parents or targets, hidden or device names). It
  needs `overwrite` plus approval to replace a file, and writes through `durable_write`.
  `sketch.import_dxf` uses `read_target` (confined for agents), `open_regular` and a 64 MiB cap.
  Reproduced: an agent's `../x.svg` and `/etc/passwd.dxf` are both `not_allowed`.
- **Output escaping.** SVG text is XML-escaped and control characters dropped; no attribute takes
  user text. DXF text drops control characters (so no group-code injection through a newline);
  layer and style names are fixed. PDF text is mapped to WinAnsi bytes and written as an escaped
  literal (`(`, `)`, `\` escaped, everything outside 0x20-0x7e as octal). The xref offsets are
  byte-exact (tested), and `/Length` counts an ASCII-only stream.
- **DXF reader input checks.** Every number must be finite and below 1e12. Polylines are capped at
  100 000 vertices and curves at 50 000. Binary DXF is refused, and the fuzz loop finds no panic.
  Importing 20 000 separate lines into a sketch takes 0.2 s in release.
- **Projection geometry.** `side_axes` gives the conventional axes (top: X right, +Y up; right: +Y
  right; bottom: -Y up). First and third angle placement, gaps, and alignment at equal scale all
  match the tests and ISO 128-30. Section planes, the removed half-space, the cutting-plane
  position in the parent and the arrow direction agree for all four sides. The arc
  direction (`ccw` from the circle axis, swapped for reversed edges, full circles one turn on) is
  consistent between the shim, the scene, SVG (sweep flag 0 with Y flipped), DXF (CCW degrees) and
  PDF (Béziers per quarter turn).
- **Dimensions.** Values are measured in model units (sheet distance / view scale, then mm or
  inch). The parallel-line distance is perpendicular. The angle vertex solves the two lines
  correctly. Diameter and radius need a face-on circle.
- **Raster size.** `render_view` validates `width` (≤ `MAX_RENDER_SIZE`), the raster clamps both
  sides to 4096 px, and the PNG is size-checked. A deep chain of views does not overflow the stack
  (9999 levels on a 2 MiB thread).
- **Approvals and read-only.** Drawing edits are `EDIT` commands through `edit`/`commit` (branch,
  rollback, validation, rate limits as for any edit). `query.drawing` is `READ`. Export is
  `WRITE_FILE` with the same overwrite approval as the other exports.
