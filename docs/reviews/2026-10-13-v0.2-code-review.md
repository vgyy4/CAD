## 2. Findings (ranked)

### High

**H1. Gear parameter edits that make the gear smaller fail with a sketch conflict on nearly every constraint. [verified]**
- Code: `crates/gusset-commands/src/gear.rs:640-700` (`profile_sketch`: every flank point placed by
  `distance` + `angle` constraints from the generation-time coordinates), `crates/gusset-commands/src/commands.rs:515`
  (`store_solution`, which `param.set` does not call), the LM solve in `gusset-eval/src/sketch.rs:182`.
- ADR 0018 §4 promises that editing `gear1_module`, `gear1_teeth`, ... in the parameter table
  reshapes the teeth. That holds only for small changes and for growing gears. Each sketch solve
  starts from the coordinates stored at generation time (`param.set` never stores solved
  positions), and from there the solver does not reach the new shape.
- Reproduction (`repro/tests/gear.rs`, mock kernel, sketch solve only):
  - `generate.gear {}` (20 teeth), then `param.set gear1_teeth`: 19 ok, **18 fails**, 21/25/40/80/150 ok.
  - Generated with 30 teeth: **29 ok, 28/27/26/25/24/22/20/19/18 fail**. Generated with 100: **95 fails**, 90/80/70 ok.
  - Generated with 20: `gear1_module` 1.9 mm ok, **1.5 mm and 1 mm fail**.
  - Every failure is `SketchConflict: constraints k4, k5, k8, k9, k11, k14, ... conflict and cannot all be satisfied`.
    The user is told to delete constraints, although the input is a valid gear (generating 18 or
    28 teeth directly works).
  - `continuation` test: from the 30-tooth document, 30→28 directly fails. 30→29→28→27 succeeds
    when each step's solution is written back into the points. So it is an initial-guess
    problem, not a geometric one.
- Existing tests only increase values (`parameter_edits_reshape_the_teeth`: 20→30, module 2→3),
  plus one invalid edit to 5 teeth.
- Fix:
  - After any edit that changes parameter values (`param.set`, `param.delete`, `document.set_text`),
    re-solve the affected sketches and store their solutions, as the sketch commands already do
    with `store_solution`.
  - Make the evaluator robust too, because a document edited as text can jump far: when a
    sketch solve fails, retry by continuation, stepping the changed parameter values from the
    last stored solution to the new values.
  - For the gear sketch in particular, seed each polar-constrained point from its own
    `distance`/`angle` values: each point is fully determined by them.
  - Add tests for decreasing teeth and module, and for a 2x jump in either direction.

**H2. A large `twist` on a sweep crashes the process (segfault in the OCCT shim). [verified]**
- Code: `crates/gusset-occt-sys/cpp/gusset_occt.cpp:598`
  `int m = int(std::ceil(std::fabs(twist) / 0.05)) + ...; m = std::min(m, 600);`. The double is
  converted to `int` before the clamp. For |twist| > about 1.07e8 rad this is undefined
  behaviour (in practice INT_MIN), so `m` goes negative and the array and loop sizes that follow
  are invalid.
- The evaluator only checks that the value is finite (`crates/gusset-eval/src/sweep.rs:19-27`).
  The shim checks only `std::isfinite(twist)`.
- Reproduction: `scratchpad/review2/docs/twist_huge.gus.txt`, a square profile swept along a
  20 mm line with `twist: 1e15 deg`. `gusset build` ends with `Segmentation fault`, exit 139.
  With `1e9 deg` and `1e7 deg` it fails cleanly ("the sweep failed").
- Impact: modeling with OCCT runs in-process on the app's model thread (only imports go to
  the sandboxed worker). Three paths reach the crash:
  - one `document.set_text` or `param.set` from an agent crashes the GUI;
  - a shared `.gus` file crashes the GUI on open;
  - after recovery is offered and accepted, the recovered document would crash the app again
    (crash loop).

  The `GS_GUARD` macros only catch C++ exceptions.
- Fix:
  - Clamp in floating point before converting:
    `double mm = std::ceil(std::fabs(twist) / 0.05); int m = int(std::min(mm, 600.0)) + ...`.
  - Validate |twist| in `run_sweep`. With 600 guide stations a twist above about 30 rad is
    undersampled anyway, so refuse more than, say, 10 turns with a hint.
  - Audit the shim for other double→int conversions. This is the only one in the v0.2 code.

**H3. Holes are cut one boolean at a time; rebuild time grows about quadratically with the hole count. [verified]**
- Code: `crates/gusset-eval/src/hole.rs:182-260`. For every site the code builds the tool,
  runs `boolean(Cut, shape, tool)` on the result of the previous cut, calls `topology()`, and
  re-runs `name_body` over the whole growing body. ADR 0019 §2 acknowledges "one boolean per
  hole (up to 1000 per feature)".
- Measurement (`scratchpad/review2/docs/holesN.gus.txt`, a 5 mm plate with an n x n grid of
  3 mm through holes from one sketch, `gusset build`, debug Rust with release OCCT):

  | Holes | Rebuild time |
  |---|---|
  | 25 | 0.47 s |
  | 100 | 5.6 s |
  | 400 | **116 s** |

  The 1,000 holes the validator allows would take on the order of 10 minutes. A release build gives
  the same numbers (0.41 / 5.56 / 105.5 s, §4): the time is in OCCT's sequential booleans.
- Perforated plates, PCB mounting grids and vent patterns are everyday parts. Every
  parameter edit upstream of the hole feature pays this again.
- Two related gaps:
  1. Holes whose sites come from a sketch have **no count limit at all**. `MAX_HOLE_SITES =
     1000` is checked only for explicit `at:` points (`commands/hole.rs:138`,
     `text.rs:1015`, `validate.rs:263`). Sketch patterns may derive up to 20,000 circles
     (`pattern.rs:19`), each a hole site (`sketch.rs:398-436`).
  2. The fit check calls `mouth_in_face` per site. Each call rebuilds the face's triangle
     list and tests 33 points against every triangle (`hole.rs:487-510`), which is again
     O(sites x triangles).
- Fix:
  - Build all tools first, then cut once with one multi-tool `BRepAlgoAPI_Cut` (OCCT's
    `SetTools` with a list; `gs_sweep` already does this for profile holes). Name the result
    once with `OpContext::Modify { inputs: [body, tool_1..tool_n] }`. Fall back to per-hole
    cuts only to locate the failing hole when the single cut fails.
  - Apply `MAX_HOLE_SITES` to the evaluated site list too.
  - Precompute the face triangles once, with a grid or bounding-box index.
  - Add a budget test (for example 400 holes under a few seconds in release) next to
    `rebuild_100_budget`.

### Medium

**M1. An undercut introduced by a later parameter edit is silent: the profile is wrong and nothing reports it. [verified]**
- Code: `crates/gusset-commands/src/gear.rs:568-574`. The derived parameter is
  `gear1_flank_roll = acos(base_r / sqrt((r - D)^2 + (D / tan a)^2))`. ADR 0018 §3 says an
  impossible edit makes it fail, citing "`acos()` of a value above 1 in `gear1_flank_roll`".
- The math shows why it never fails. `R(D)^2 = (r - D)^2 + D^2 / tan^2 a` is smallest at
  `D = r sin^2 a`, where `R = r cos a = r_b`. So `R >= r_b` for every `D`, the `acos` argument
  never exceeds 1, and the undercut condition `D > r sin^2 a` produces no error. The generator
  itself checks the condition explicitly (`gear.rs:155-157`), but the parametric sketch does not.
- Reproduction (`repro/tests/gear.rs::undercut_edit_small_steps`): generate 12 teeth with shift
  0.4, then set `gear1_shift` to 0.25 and then 0.2. `Geometry::new` refuses both ("12 teeth with a
  20 deg pressure angle would be undercut"), yet the sketch evaluates **WellConstrained** with
  areas 448.3 / 441.0 mm2. The extruded gear would not mesh as computed: the involute starts
  below the true limit of the generated flank.
- Fix: add an explicit guard parameter that fails when undercut, for example
  `gear1_undercut_margin = sqrt(pd/2 * sin(ta)^2 - dj)`, or a `max(0, ...)` that feeds a
  `sqrt` of a negative value. Reference it from the first involute point's expression so the
  sketch fails with a named parameter. Add a test that edits a valid gear into undercut by
  shift and by teeth. Correct ADR 0018 §3 accordingly.

**M2. A recovery write that completes clears the "unsaved changes" counter, including changes made while it was being written. [verified by code trace]**
- Code:
  - `crates/gusset-app/src/app.rs:592-596`: `Done::Recovery(r)` calls `self.save.written()`
    when `r.is_ok()`.
  - `crates/gusset-project/src/settings.rs:325-328`: `written()` sets `pending = 0` and
    `pending_since = None`.
  - `crates/gusset-app/src/app.rs:446-451`: every `HostEvent::Changed`, including agent edits,
    calls `save.changed()`.
- Before M3 the snapshot ran on the model thread, and its reply was ordered with the command
  replies. Now the bytes are encoded at one point (`prepare_snapshot`), the write runs on
  another thread for up to about 0.5 s, and `written()` runs when the write finishes.
- Scenario:
  1. The snapshot of state S is prepared.
  2. While it is being written, the user or an agent makes edits E1..Ek. Each calls `changed()`.
  3. The write of S finishes, `written()` sets `pending = 0`, and E1..Ek are no longer tracked.
  4. The user stops editing. No further snapshot is scheduled (`due()` returns `Nothing` while
     `pending == 0`).
  5. A crash loses E1..Ek, although the recovery interval elapsed.

  A write skipped by the generation gate (`Ok(None)`) also counts as written.
- Fix: snapshot the change counter at prepare time (put a change sequence number into
  `SnapshotWrite` or the `Done` message) and on completion subtract only the changes that were
  in the snapshot (`written_upto(seq)`). Treat `Ok(None)` as "not written". Add a scheduler
  unit test with interleaved `changed()` and completion.

**M3. Release workflow: a manual run can move an existing tag and replace the files of an already published release. [verified by reading]**
- Code: `.github/workflows/release.yml`:
  - `:356-362` force-PATCHes `refs/tags/$RELEASE_TAG` to the new commit;
  - `:431-435`: `gh release upload ... --clobber` when a release already exists, published
    or not, without `--verify-tag`.
- Impact:
  - Any run started with `workflow_dispatch` and a tag matching the workspace version silently
    rebuilds a published release from a different commit and overwrites its assets.
  - Users who downloaded earlier hold files that no longer match `SHA256SUMS`, and there are
    two sets of attestations for one version.
  - The tag no longer identifies the source. This weakens the provenance story of ADR 0013/0015.
- Fix:
  - Refuse to move a tag that already points to a different commit when a non-draft release
    exists; allow the move only for drafts, or require a new version or tag.
  - Never use `--clobber` on a published release.
  - Record the decision in the ADR 0013 amendment.

**M4. Hole preset table: the DIN 974-1 counterbore depths cannot be traced to a standard and are internally irregular. [suspicion; see §3]**
- Code: `crates/gusset-commands/src/hole_standards.rs:79-95`.
- The depth minus the head height `k` is 0.4, 0.4, 0.4, 0.5, 0.6, 0.8, 0.6, 0.5, 0.5, 0.5, 0.5 mm
  for M3...M24. It rises to M10 and then falls again. No published series has that shape.
- ADR 0019 §5 already says the values were "written from memory".
- Everything else checked in §3 matches the published nominal values.
- Impact: socket-head screws seated in a counterbore made by the preset may stand proud or sit
  deeper than intended. The values are parameters, so a wrong value is easy to fix but easy to
  miss.
- Fix:
  - Take the depths from one documented rule and cite it, for example "head height `k` max +
    the DIN 974-1 allowance for the series", or from the owner's copy of DIN 974-1:2008.
  - Add the remaining spot checks to `table_is_consistent`.
  - Until then, mark the depth comment in the parameter as "not verified".

**M5. Gear and other model-defining code use the platform `libm` (std `sin/cos/tan/acos/atan2`), not the deterministic `libm` crate. [suspicion]**
- Code:
  - `crates/gusset-commands/src/gear.rs` (20 calls; the fit-point choice in `refine` and the
    coordinates written into the document);
  - `crates/gusset-eval/src/datum.rs:98` (`sin_cos` for angled datum planes);
  - `crates/gusset-eval/src/hole.rs` (`tan` for drill-point and countersink depth).
- In contrast, `gusset-eval/src/pattern.rs:43` uses `libm::sin/cos`, and gusset-units uses
  `libm` throughout ("deterministic, libm").
- PROMPT.md §Determinism requires model-defining code to give the same result on every CPU
  and platform. glibc, MSVC and Apple libm differ in the last ulp for these functions. On the
  gear this can change the bisection decisions (the number and position of fit points) and
  the coordinates written to the file, so the same `generate.gear` call would produce different
  documents on Windows and Linux.
- Fix: use `libm::` in model-defining code, and add a clippy `disallowed-methods` list for
  `f64::sin` etc. in the model crates.

### Low

**L1. `combine` with `op: cut` or `intersect` copies the tool bodies' hole records into the target. [verified by code]**
- Code: `crates/gusset-eval/src/ops.rs:429-447`. `tool_holes` is appended for every operation.
  Subtracting a body that has a tapped hole makes `query_body` report a cosmetic thread on the
  target that does not exist.
- More generally, records are never pruned when their wall face disappears, for example after
  a later cut removes the region.
- Fix: merge records only for union, and drop records whose `wall` face is no longer in
  `names` after any modification.

**L2. Hole ids for explicit points are list positions (`e1`, `e2`, ...). [verified by code]**
- Code: `crates/gusset-eval/src/hole.rs:433`.
- Deleting or reordering an `at:` entry renames every later hole's faces (`Hole1/wall(e3)`
  becomes `wall(e2)`). Downstream references then silently move to a different hole: same
  feature, valid name. That is the instability ADR 0003 tries to avoid.
- Fix:
  - Document the limitation in ADR 0019 §3, and prefer sketch points (stable ids) in the
    command hint.
  - Or give `at:` entries stored ids.

**L3. The direction of an angled datum plane's edge axis is canonicalised with an absolute 1e-9 test on the unit vector's components. [suspicion]**
- Code: `crates/gusset-eval/src/datum.rs:90`.
- An edge meant to be perpendicular to X can carry an x component of order 1e-9 from boolean
  results (OCCT vertex tolerance is 1e-7 mm). If its sign flips between rebuilds, the rotation
  direction flips and the plane turns the other way.
- Fix: use a relative threshold of about 1e-6.

**L4. `compact_result` rounds every float to an absolute 1e-6. [verified by code]**
- Code: `crates/gusset-mcp/src/server.rs:222-245`.
- Any value below 5e-7 becomes 0 and small values lose relative precision. Affected values
  include `flank_error_mm` (about 4e-7), small areas or volumes in mm2/mm3, tolerances, and
  angles in radians near 0.
- Fix: round to about 12 significant digits instead of a fixed number of decimals.

**L5. The release concurrency group differs between the two triggers. [verified by reading]**
- Code: `.github/workflows/release.yml:33`. A tag push uses `release-refs/tags/vX`, a manual
  dispatch `release-vX`.
- A push run and a dispatch run for the same tag are therefore not serialised and can race on
  `gh release create/upload`.
- Fix: use `release-${{ inputs.tag || github.ref_name }}`.

**L6. Pre-release and release MSIs get the same `ProductVersion`. [verified by reading]**
- Code: `release.yml` `numeric=${version%%-*}`. 0.1.0-mvp and 0.1.0 are both built as 0.1.0.
- Windows Installer `MajorUpgrade` does not upgrade between equal versions unless
  `AllowSameVersionUpgrades` is set, so installing 0.1.0 over 0.1.0-mvp can leave two entries
  or refuse.
- Fix: map pre-releases to a lower fourth field, or set `AllowSameVersionUpgrades`.

**L7. The hole fit check samples only 33 points of the mouth disc. [verified by code]**
- Code: `hole.rs:487-510`.
- A small existing hole or slot inside the mouth, between the centre and the sample circle or
  between samples (the spacing is about 2 mm on a 20 mm counterbore), passes the check. The
  cut still works; the friendly error is just not given.
- Fix: test the face's boundary loops against the mouth circle, not only the circle against
  the triangles.

**L8. `hole_standards.rs` doc comment says DIN 974-1 does not cover M1.6. [suspicion]**
- Code: `crates/gusset-commands/src/hole_standards.rs:18`.
- The DIN 974-1 series for ISO 4762 starts at M1.6 (3.5, 4.4 and 5.5 mm for M1.6, M2 and M2.5,
  from memory of the table), and ISO 4762 itself covers M1.6 upward.
- Fix: correct the comment, and add the rows once they are verified.

**L9. The "teeth come to a point" hint is garbled. [verified]**
- Code: `gear.rs:202`. The hint reads "use a smaller profile shift, more backlash is not

- The 0.1 m tip-land limit is also lower than common practice. DIN 3960 / ISO 21771 guidance

**L10. The fuzz corpus has no seeds for the v0.2 grammar. [verified]**
- `fuzz/` changed only in its lockfile. `doc_text` checks the print/parse fixed point, but
  seeds for `hole`, `sweep`, `loft`, `plane`, `move`, `combine`, `shell`, `mirror`, the

**L11. Spline segments between duplicate fit points are emitted as zero-length Béziers. [suspicion]**
- Code: `crates/gusset-sketch/src/spline.rs:58-60`, `[p1, p1, p2, p2]` with `p1 == p2`.

### Gear math (`gear.rs`)
Checked against the textbook formulas (Niemann/Winter, ISO 21771 notation):
- Tooth thickness. `half = (pi/2 + 2 x tan a_n - b/m_n) / z` is the transverse half-angle on the
  pitch circle, also for helical gears:
  - `s_t = m_t (pi/2 + 2 x tan a_t)` and `x m_n tan a_t = x m_t tan a_n`, so the normal angle
    is the right one in the formula;
  - normal backlash b becomes `b / cos(beta)` in the transverse section, and `b_t / m_t = b / m_n`.
  - `tooth_angle = half + inv(a_t)` is the base-circle half-angle. Correct.
- Pitch, base, tip and root diameters: `d = m_t z`, `d_b = d cos a_t`, `d_a = d + 2 m_n (1 + x)`,
  `d_f = d - 2 m_n (1.25 - x)`. Correct for ISO 53 profile A (no tip shortening for shifted
  pairs, which ADR 0018 lists as "not included").
- Involute: `r = r_b / cos(phi)`, polar angle `inv(phi) - theta_b`. Correct. "Roll angle" in
  the names is really the pressure angle at the point; harmless.
- Trochoid root fillet (rack tip radius 0.38 m_n, centre at depth `(1.25 - x) m_n - rho`,
  offset `pi m_t / 4 - (h + x m_n) tan a_t - rho / cos a_t`), and the junction at depth
  `D_J = h + rho sin a_t`. Correct envelope construction. For x = 0 and rho = 0.38 the undercut
  limit `D_J <= r sin^2 a` gives z_min = 2(1.25 - 0.38 (1 - sin 20 deg)) / sin^2 20 deg = 17.1,
  the classical 17.
- Helical: `m_t = m_n / cos(beta)`, `tan a_t = tan a_n / cos(beta)`, twist `b tan(beta) / r`.
  Correct.
- Issues: the parametric undercut guard does not work (M1), parameter edits fail (H1), the
  tip-land limit and hint (L9), determinism (M5).

## 5. What is good
- **Every layer is covered for each feature kind.** Each one comes with text grammar,
  validation, rename/dependency handling (`ops::rename_refs`, `FeatureKind::dependencies`),
  evaluator, MCP schema and tests. The rename paths cover every new reference (sweep paths,
  loft profiles, hole sketches, datum bases, combine tools, nested face keys).
- **Persistent naming is designed, not improvised.**
